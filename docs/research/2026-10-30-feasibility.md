# Feasibility research, 2026-10-30

This note summarizes the research that led to the project: should Open5GS be translated to Bend 2, or a 5G core written in Bend 2? The conclusion was no to a translation and no to a GPU data plane, yes to a verified spec kernel. Every fact is dated; Bend 2 changes weekly, so re-check before relying on any of it.

## Open5GS v2.8.0, measured

Measured on commit `157f611` (2026-06-20) with tokei 15.0.0, counting lines of C code without comments or blank lines.

| Category | Lines |
|---|---|
| Hand-written | 262,110 (70,929 of them tests) |
| Generated | 1,119,194 |
| · NGAP (Next Generation Application Protocol), asn1c | 409,723 |
| · S1AP (the 4G antenna protocol), asn1c | 202,491 |
| · SBI (Service-Based Interface) models, OpenAPI generator | 463,273 |
| · NAS / GTP / PFCP codecs, generated by Python scripts | 27,832 / 7,951 / 7,924 |
| Vendored in tree | 30,367 |

Hand-written lines per network function:

| Function | Lines |
|---|---|
| AMF (Access and Mobility Management Function) | 25,302 |
| SMF (Session Management Function); about 5,800 lines are 4G-only interfaces | 29,296 |
| UPF (User Plane Function) | 3,537 |
| AUSF (Authentication Server Function) | 1,686 |
| UDM (Unified Data Management) | 3,579 |
| UDR (Unified Data Repository) | 1,901 |

**Logic and I/O are interleaved.** The AMF's handlers and state machines make a side-effecting call (send a message, start a timer, allocate memory) every 33 lines; the SMF's, every 24. Porting that logic means redesigning it as a function from (state, event) to (new state, actions).

**Licence.** Open5GS is AGPL-3.0, so a translation would be a derivative work.

## Bend 2, read in primary sources (as of 2026-10-30)

- **Where it lives.** Repo: [bendlang/bend](https://github.com/bendlang/bend), Apache-2.0. Bend 2 is a from-scratch rewrite launched 2026-09-17; the latest release is v2.0.39 (2026-10-23). "bend3" was its internal name.
- **Proofs.** `--verdict` re-checks a program with a kernel written in Lean that has consistency proofs. The everyday checker, the parser and the translation into the kernel are not proven. The type theory is Type : Type, kept consistent through affinity. There are no tactics.
- **Targets.** C, CUDA, Metal and JavaScript. Only pure functions called with `!` run on the GPU. There is no native-library target.
- **I/O.** Files, TCP, UDP (IPv4 only), timers, processes and channels. There is no SCTP (Stream Control Transmission Protocol), IPv6, raw sockets, TLS or HTTP.
- **C FFI.** Only as I/O effects, and only with handle types the base library already declares.
- **Numbers and bytes.** Only Nat, U32 and F32 exist; there is no U64. Byte buffers are linked lists of U32.
- **HVM.** Bend 2 does not run on HVM. Parallelism comes from BendRT's fork-join scheduler.
- **SupGen.** Not public; it is internal research.
- **Risks.** The compiler is "99% AI-written and not yet fully audited", and breaking changes land even in patch releases.

## Other cores (as of 2026-10-30)

- **[Ella Core](https://github.com/ellanetworks/core) v1.11.1.** The best architectural reference for a single-process design: the 5G functions call each other in-process, it has its own small PER (Packed Encoding Rules) codec, and v1.11.1 is the last Apache-2.0 release (later versions are BUSL-1.1).
- **[free5GC](https://github.com/free5gc/free5gc).** Apache-2.0, written in Go; a good per-function reference.
- **Open5GS.** The best reference for the method of generating codecs from the 3GPP (3rd Generation Partnership Project) spec tables.

## Formal verification landscape

Model-level proofs of 5G authentication exist in Tamarin:

- [Basin et al., CCS 2018](https://arxiv.org/abs/1806.10360)
- [Cremers and Dehnel-Wild, NDSS 2019](https://www.ndss-symposium.org/wp-content/uploads/2019/02/ndss2019_06B-1_Cremers_paper.pdf)

At the implementation level we found nothing verified for 3GPP: no NAS (Non-Access Stratum), NGAP or PFCP (Packet Forwarding Control Protocol) codec, no core state machine and no Milenage. The closest work is [VUPER](https://arxiv.org/abs/2608.09094), a parser verified in Rocq. It handles UPER (Unaligned PER) for radio messages, but not the APER (Aligned PER) that NGAP uses, and not NAS.

## User plane on GPU: rejected

No GPU UPF exists, either in papers or products, from 2019 to 2026. NVIDIA puts its UPF on a DPU (data processing unit).

The CPU matches or beats the GPU for simple packet forwarding, because a round trip to the GPU costs 50 µs or more:

- [Kalia et al., NSDI 2015](https://www.pdl.cmu.edu/ftp/associated/gopt_nsdi.pdf)
- [APUNet, NSDI 2017](https://www.usenix.org/system/files/conference/nsdi17/nsdi17-go.pdf)

Open5GS's own UPF manages about 1.4 Gbps, against about 9 Gbps for eUPF on XDP in the same VM ([s5uishida](https://github.com/s5uishida/simple_measurement_of_upf_performance_10)).
